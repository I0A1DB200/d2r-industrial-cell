00 · Brief del cliente y requisitos iniciales

Versión: 0.2 · base didáctica aprobada por D2R Fecha: 2026-11-12 Caso: D2R Inspection Cell · cliente ficticio Fuente para describir el simulador: prototipo funcional

Importante: no existe un cliente real ni un brief firmado. D2R aprobó este caso ficticio y sus decisiones para uso didáctico el 2026-11-12. Los valores marcados como supuesto didáctico siguen sin ser datos medidos, una compra aprobada ni una especificación de una instalación real; deberán sustituirse si se reciben datos auténticos de cliente o emplazamiento.

1. Encargo didáctico

Una empresa ficticia de mecanizado quiere automatizar la inspección visual de una placa pequeña y clasificarla automáticamente. Una persona operadora carga piezas en un cargador, inicia la célula desde el HMI, recoge las piezas buenas y las rechazadas en dos contenedores y consulta el resultado de cada pieza en un registro electrónico.

La célula de aprendizaje es autónoma: la carga inicial y la retirada de contenedores son manuales. No se presupone una línea anterior o posterior, ni comunicación con MES/ERP. La persona de mantenimiento e ingeniería podrá observar señales y diagnosticar el ciclo.

El ejercicio recorrerá el ciclo de vida completo: requisitos, concepto mecánico y eléctrico, selección de hardware, arquitectura y programa PLC, Safety Engineering, HMI/visión y commissioning. El HTML actual permite estudiar y demostrar el proceso; no ejecuta una máquina física.

2.2 Decisión de inspección

Para el primer caso, la cámara debe devolver OK cuando se identifican los cinco taladros y NOK si falta o está visiblemente obstruido cualquiera de ellos. La célula no promete medir diámetros ni sustituir un calibre. Los criterios se limitarán a esta regla para que los resultados puedan explicarse y probarse con muestras conocidas.

3. Operación y objetivos de producción

3.1 Supuestos de operación

  • Un turno de 8 horas al día, 5 días por semana.
  • Objetivo de capacidad: 5 piezas por minuto en régimen estable, equivalente a un intervalo medio de 12 s entre piezas.
  • El objetivo no incluye la carga manual del cargador, vaciado de contenedores, pausas planificadas ni resolución de atascos. El tiempo de ciclo real y la disponibilidad se medirán en una máquina construida; los tiempos del simulador no sirven para demostrar este objetivo.
  • El operador carga hasta 7 piezas en el cargador y coloca contenedores vacíos en A y B. La pila de siete es también el lote gráfico del simulador, no una limitación de producción aprobada.
  • Capacidad propuesta de cada contenedor: 25 piezas. El operador los vacía o cambia; no se presupone sensor de contenedor lleno en esta etapa.
  • Una referencia de producto, alimentación manual por lote, descarga manual y sin enlace de control con otras máquinas.
  • El HMI de operador estará en español. La documentación del proyecto se entregará en español e inglés.

El objetivo de 5 piezas/minuto es una meta inicial para analizar el presupuesto de ciclo, no una prestación ya alcanzada. Si el tiempo de visión, la mecánica o la manipulación no permiten sostenerla, se debe revisar el requisito con los resultados del piloto.

3.2 Flujo esperado

  1. El operador confirma que la zona está despejada, carga piezas y coloca los contenedores A/B.
  2. Selecciona AUTO para procesar de forma continua mientras haya producto, o PIEZA para solicitar una unidad con START.
  3. El alimentador presenta una pieza en la cinta y esta llega a inspección.
  4. La cinta se detiene para la adquisición. El PLC activa el trigger de cámara y espera una respuesta válida.
  5. Una pieza OK se dirige a A; una pieza NOK se dirige a B.
  6. El sistema confirma la salida, incrementa el contador correspondiente y genera un registro por pieza.
  7. FIN DE PIEZA solicita detenerse una vez completada la pieza en curso. El rearme/reset se realiza con la máquina parada, según la interfaz finalmente aprobada.

Este flujo describe el caso que se diseñará. La secuencia y mandos que actualmente representa el HTML se enumeran por separado en la sección 8 para no confundir comportamiento simulado con requisito físico validado.

5. Interfaces de visión y trazabilidad

5.1 Intercambio con la cámara

El caso propone una cámara inteligente Cognex, sin fijar todavía modelo, lente, iluminación o protocolo. El PLC deberá solicitar una captura después de confirmar la presencia y posición de pieza. La interfaz conceptual deberá distinguir, como mínimo:

  • PLC → cámara: selección de receta/job, trigger y número de pieza/lote si el equipo lo admite.
  • Cámara → PLC: ready, busy, complete, resultado válido, resultado OK/NOK y código de resultado.
  • PLC ↔ cámara: reconocimiento o limpieza del resultado anterior para evitar reutilizar una respuesta vieja.
  • Diagnóstico: tiempo de espera, pérdida de comunicación, receta no disponible o respuesta inválida; la conducta de recuperación se diseña y prueba antes de la aceptación.

“Trigger” no queda fijado como una entrada eléctrica dedicada: podrá ser E/S discreta o una orden por red según el modelo seleccionado. Los nombres anteriores describen contenido de la interfaz, no tags asignados ni direcciones físicas. El mapa definitivo y los tipos se documentarán en los documentos de hardware y arquitectura PLC.

5.2 Registro electrónico externo

El caso requiere un registro electrónico por pieza con retención mínima propuesta de 30 días. La base puede ser un servicio SQL externo accesible a través de un gateway/servicio de planta; el PLC no se considera cliente SQL directo. El transporte, servidor, formato, sincronización horaria, política ante desconexión y responsable de administrar la base quedan abiertos para el diseño de integración. No se almacenan imágenes en la propuesta inicial.

El registro mínimo propuesto es: batch_id, piece_index, timestamp, product_id, vision_job, inspection_result, result_code, destination y machine_state. Cada ID debe permitir relacionar la respuesta de la cámara, el contador del PLC y la salida física. Una escritura fallida debe generar un estado/diagnóstico verificable y una política acordada; no se debe marcar un registro como guardado si no se confirmó su persistencia.

7. Safety y límites de responsabilidad

El proyecto deberá evaluar, como mínimo, acceso a cinta y alimentador, movimiento del expulsor, posibles puntos de atrapamiento, energía neumática almacenada, recuperación de atascos y tareas de limpieza/mantenimiento. La evaluación determinará medidas, distancias, arquitectura, nivel requerido y validación conforme a la normativa aplicable al emplazamiento.

Este brief no elige un nivel PLr/SIL, no declara conformidad, no convierte resguardos gráficos en resguardos certificados y no aprueba una solución Safety. SafetyReady en el simulador es una señal conceptual fija; no representa un circuito de seguridad. Ningún valor de este caso didáctico sustituye una evaluación realizada por personas competentes.

8. Hechos del simulador y límites de evidencia

El HTML actual sirve para observar un modelo gráfico y su lógica simulada. Concretamente:

  • La demostración presenta un lote fijo de siete resultados: OK, NOK, OK, NOK, OK, OK, NOK (cuatro OK y tres NOK). Es una secuencia de prueba de rutas, no una tasa esperada de defectos.
  • La ruta representada es OK → A por expulsor lateral y NOK → B al final de la cinta.
  • AUTO recorre el lote; PIEZA permite solicitar una unidad con START; FIN DE PIEZA termina la pieza en curso antes de detenerse.
  • La cámara no captura ni analiza imágenes. El resultado procede de la secuencia didáctica programada.
  • La geometría, dimensiones, trayectorias y tiempos del HTML son visualización/temporización del modelo. No son tolerancias, capacidad, fuerza, respuesta ni rendimiento físico medido.
  • PLC Watch contiene señales conceptuales; no hay direcciones I/Q, CPU, DB físicos ni conexión a PLC.
  • No existe cámara Cognex conectada, servicio externo de datos, DB persistente, receta real ni trazabilidad activa.
  • La interfaz incluye estados de operación, diagnóstico y permiso Safety conceptual; ninguno constituye una validación de máquina.

Cuando este documento dice “criterio del simulador”, solo significa que el comportamiento visible puede observarse en la demostración. No demuestra cumplimiento de una prueba física.

9. Fuera del alcance de este primer brief

  • Fabricar una máquina o liberar dibujos para construcción.
  • Determinar tolerancias finales sin plano del producto ni acuerdo de calidad.
  • Prometer que 5 piezas/minuto, la tasa de detección o la disponibilidad ya se han alcanzado.
  • Seleccionar modelos de PLC, HMI, cámara, lente, iluminación, motor, válvulas o protecciones.
  • Asignar direcciones de E/S, declarar tags existentes en TIA o conectar una DB.
  • Escribir/validar el programa PLC, implementar comunicaciones o desarrollar una aplicación de trazabilidad.
  • Definir, certificar o validar funciones de Safety a partir del simulador.

Version: 0.2 · teaching baseline approved by D2R Date: 2026-11-12 Case: D2R Inspection Cell · fictional client Source used to describe the simulator: functional prototype

Important: no real client or signed brief exists. D2R approved this fictional case and its decisions for teaching use on 2026-11-12. Items marked as a teaching assumption are still not measured data, an approved purchase, or a specification for a real installation; replace them if genuine customer or site data becomes available.

1. Teaching assignment

A fictional machine shop wants to automate visual inspection of a small plate and sort each part automatically. An operator loads parts into a magazine, starts the cell from the HMI, collects good and rejected parts in two bins, and reviews each part in an electronic record.

The learning cell is standalone: initial loading and bin removal are manual. No upstream or downstream line, or MES/ERP communication, is assumed. Maintenance and engineering personnel can observe signals and diagnose the cycle.

The exercise follows the full project lifecycle: requirements, mechanical and electrical concept, hardware selection, PLC architecture and program, Safety Engineering, HMI/vision, and commissioning. The current HTML is for study and demonstration; it does not operate physical machinery.

2. Part and inspection scope

2.2 Inspection decision

For the first case, the camera shall return OK when all five holes are identified and NOK if any hole is missing or visibly obstructed. The cell does not promise diameter measurement or replace a gauge. The criteria are limited to this rule so results can be explained and tested with known samples.

3. Operation and production targets

3.1 Operating assumptions

  • One 8-hour shift per day, 5 days per week.
  • Capacity target: 5 parts per minute at steady state, equivalent to an average 12-second interval between parts.
  • This target excludes manual magazine loading, bin emptying, planned breaks, and jam recovery. Actual cycle time and availability must be measured on a built machine; simulator timing cannot demonstrate this target.
  • The operator loads up to 7 parts in the magazine and places empty bins at A and B. The seven-part stack is also the simulator's graphical batch, not an approved production limitation.
  • Proposed capacity of each bin: 25 parts. The operator empties or changes bins; no full-bin sensor is assumed at this stage.
  • One product reference, manual batch loading and unloading, and no control link to other machines.
  • The operator HMI is in Spanish. Project documentation is delivered in Spanish and English.

The 5 parts/minute target is an initial goal for cycle-budget analysis, not a demonstrated performance. If vision, mechanics, or handling cannot sustain it, revise the requirement using pilot results.

3.2 Expected flow

  1. The operator confirms the area is clear, loads parts, and places the A/B bins.
  2. The operator selects AUTO for continuous processing while product is available, or PIEZA to request one unit with START.
  3. The feeder presents one part on the conveyor and it travels to inspection.
  4. The conveyor stops for image acquisition. The PLC triggers the camera and waits for a valid response.
  5. An OK part is sent to A; an NOK part is sent to B.
  6. The system confirms the output, increments the matching counter, and creates one record per part.
  7. FIN DE PIEZA requests a stop after the active part is completed. Reset/rearm takes place with the machine stopped, according to the interface eventually approved.

Controls for the teaching case: START requests a start when start conditions are satisfied; FIN DE PIEZA finishes the active part and prevents another from starting; HMI RESET is only available while the machine is stopped. Pause and SIM RESET belong to the graphical teaching environment and are not treated as PLC commands for the real machine. The scope and meaning of a physical pause must be decided in the functional design.

This flow describes the case to be designed. The sequence and controls currently represented by the HTML are listed separately in section 8 to avoid confusing simulated behavior with a physically validated requirement.

5. Vision and traceability interfaces

5.1 Camera exchange

The case proposes a Cognex smart camera, without yet selecting model, lens, lighting, or protocol. The PLC shall request an acquisition after confirming part presence and position. At a conceptual level, the interface must distinguish at least:

  • PLC → camera: recipe/job selection, trigger, and batch/part number if supported by the device.
  • Camera → PLC: ready, busy, complete, valid result, OK/NOK result, and result code.
  • PLC ↔ camera: acknowledgement or clearing of the previous result to avoid reusing stale data.
  • Diagnostics: timeout, communication loss, unavailable recipe, or invalid response; recovery behavior must be designed and tested before acceptance.

“Trigger” is not fixed as a dedicated electrical input: it may use discrete I/O or a network command depending on the selected model. The names above describe interface content, not assigned tags or physical addresses. The final map and types will be documented in the hardware and PLC architecture documents.

5.2 External electronic record

The case requires an electronic record per part with a proposed minimum retention of 30 days. The database may be an external SQL service accessed through a plant gateway/service; the PLC is not treated as a direct SQL client. Transport, server, format, time synchronization, disconnection policy, and database administrator remain open for integration design. The initial proposal does not store images.

The proposed minimum record is: batch_id, piece_index, timestamp, product_id, vision_job, inspection_result, result_code, destination, and machine_state. Each ID must relate the camera response, PLC counter, and physical output. A failed write must create a verifiable state/diagnostic and an agreed policy; a record must not be marked saved unless persistence is confirmed.

7. Safety and responsibility limits

At minimum, the project must assess access to the conveyor and feeder, pusher movement, possible trapping points, stored pneumatic energy, jam recovery, and cleaning/maintenance tasks. The assessment will determine measures, distances, architecture, required performance level, and validation under the regulations applicable to the site.

This brief does not select a PLr/SIL, declare conformity, turn graphical guards into certified guards, or approve a Safety solution. SafetyReady in the simulator is a fixed conceptual signal; it does not represent a safety circuit. No value in this teaching case replaces an assessment by competent people.

8. Simulator facts and evidence limits

The current HTML is a graphical model with simulated logic. Specifically:

  • The demonstration has a fixed batch of seven results: OK, NOK, OK, NOK, OK, OK, NOK (four OK and three NOK). It is a route test sequence, not an expected defect rate.
  • Represented routing is OK → A via the side pusher and NOK → B at the end of the conveyor.
  • AUTO runs the batch; PIEZA requests one unit with START; FIN DE PIEZA finishes the active part before stopping. HMI RESET is restricted to a stopped state. Pause and RESET SIM control the teaching environment, not machine PLC logic.
  • The camera does not capture or analyze images. Results come from the programmed teaching sequence.
  • HTML geometry, dimensions, paths, and times are visualization/model timing. They are not physical tolerances, capacity, force, response, or measured performance.
  • PLC Watch contains conceptual signals; there are no I/Q addresses, CPU, physical DBs, or PLC connection.
  • No Cognex camera, external data service, persistent DB, real recipe, or active traceability is connected.
  • The interface includes operating states, diagnostics, and a conceptual Safety permission; none is machine validation.

When this document says “simulator criterion,” it only means that visible behavior can be observed in the demonstration. It does not demonstrate compliance with a physical test.

9. Out of scope for this initial brief

  • Building a machine or releasing construction drawings.
  • Setting final tolerances without a product drawing and quality agreement.
  • Claiming that 5 parts/min, inspection rate, or availability have already been achieved.
  • Selecting PLC, HMI, camera, lens, lighting, motor, valves, or protective-device models.
  • Assigning I/O addresses, declaring existing TIA tags, or connecting a database.
  • Writing/validating PLC software, implementing communications, or developing traceability software.
  • Defining, certifying, or validating Safety functions based on the simulator.
